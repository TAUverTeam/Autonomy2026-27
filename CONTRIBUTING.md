# Contributing

How to get your work into this repository. Read [docs/documentation-standard.md](docs/documentation-standard.md)
first: it defines what "documented" means here.

## The short version

1. Create a branch from `main`.
2. Write the code **and** its documentation.
3. Test it, and write down how you tested it.
4. Open a pull request, paste the reviewer checklist, and ask a teammate to review.
5. Fix what the reviewer asks for. They merge it.

Nobody pushes directly to `main`, including the team leader.

## Branches

| Branch | What it holds |
|---|---|
| `main` | Reviewed code that builds. May not yet be tested on the rover. |
| `<name>/<short-topic>` | Your work in progress, for example `dana/landmark-detector`. |

Tested versions are marked with tags, not branches (see [Versions](#versions)).

Keep branches short-lived: a few days, not weeks. Large features are split into small pull requests
that each work on their own.

## Pull requests

A pull request description contains:

- **What**: what changed, in a few sentences.
- **Why**: the problem it solves, with requirement IDs (for example `REQ-AUT-020`).
- **How it was tested**: commands, recordings used, results. "Not tested on the rover yet" is fine, if
  it is said.
- **The reviewer checklist** from [docs/documentation-standard.md](docs/documentation-standard.md#reviewer-checklist).

### Reviewing

The reviewer:

- builds the branch and runs the tests described,
- reads the documentation as if they were new to the team: can they run it from the README alone?
- ticks the checklist, or comments on each item that is missing.

Reviewing is how the team learns each other's code. Every member reviews regularly.

## What never goes into the repository

| Do not commit | Why | Where it goes instead |
|---|---|---|
| `build/`, `install/`, `log/` | Generated by `colcon build`; they differ per machine | Nowhere. Ignored by `.gitignore` |
| Recordings (ROS bags, `trial_*`), videos | Too large for Git | The team's shared storage. Link them from `docs/measurements/` |
| Trained model weights over a few MB | Too large | Shared storage, with a download script in the package |
| Passwords, keys, tokens | Anyone with repository access would see them | Ask the team leader |
| Other teams' code | This repository is Autonomy only | Their own repositories |

Third-party code we must change (for example a camera driver) is not copied in. We use the upstream
version and keep our changes as a documented patch or a fork, with a decision record explaining why.

## Versions

When a version has been tested on the rover:

1. Add an entry to [CHANGELOG.md](CHANGELOG.md): date, what was tested, where, and the result.
2. Tag the commit with the test date and push the tag:

   ```bash
   git tag -a v2027.03.14 -m "Field test at <place>: 4 waypoints reached"
   git push origin v2027.03.14
   ```

## Questions

Ask in the team chat. If the answer was not in the docs, add it to the docs.
